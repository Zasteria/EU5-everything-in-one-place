# ==========================================================================
# WHY THESE HOOKS LOOK INDIRECT
#
# An on_action's `effect` is a SINGLE-VALUE field. When two files declare
# `effect` for the same on_action the engine keeps one and silently discards
# the other, logging only "There is more than one 'effect' defined using most
# recent: <file>". Vanilla never does this: across all 164 vanilla on_actions
# there are zero cases of two files declaring the same field. Paradox avoids
# it with a chain: ai_personalities_setup.txt adds
# `on_actions = { on_ai_personalities_game_start }` to on_game_start rather
# than a second `effect`.
#
# This file used to declare `effect` directly on `on_game_start` (colliding
# with _hardcoded.txt) and on `on_four_yearly_check_for_script` (colliding
# with country_four_yearly.txt). Our file sorts before both alphabetically, so
# vanilla parsed last and won, and BOTH of our effects were dropped: no
# destiny trees for the 20 game-start tags below (the Austria/Bohemia/Poland
# Workshop reports) and no BYZ achievement gate. It also used
# `on_country_yearly_pulse`, which is not an engine on_action at all. The
# name appears nowhere in vanilla, so it was never called and the DNM
# succession chain never fired.
#
# Rules for editing this file:
#   * Before declaring a field on a vanilla on_action, check that no vanilla
#     file already declares that same field on it. `eu5-validate --checks
#     on_actions` enforces this.
#   * Engine periodic country hooks are `monthly_country_pulse`,
#     `biyearly_country_pulse`, `yearly_country_pulse`,
#     `four_yearly_country_pulse` (no `on_` prefix). An `on_`-prefixed pulse
#     name is almost certainly invented and will never fire.
#   * Slot ledger as of 2026-09-10: WE hold monthly_country_pulse.effect
#     (bootstrap + DNM chain + France unlock + Danube spark watch + AI
#     formables),
#     on_four_yearly_check_for_script.on_actions (BYZ achievement),
#     on_new_ruler.on_actions (Danube succession checkpoint) and, since
#     2026-10-01, on_losing_war.on_actions (Danube throne war). Still free:
#     biyearly_country_pulse.effect, on_country_specific_pulse.{effect,
#     on_actions}. Re-verify against vanilla after every patch.
# ==========================================================================

# Fire formation events at game start for tags that exist as already-formed countries.
# Without this, players starting as e.g. Bohemia never get their destiny tree because
# the formation event (which sets nd_TAG_formed) only fires when the country is formed
# from an unformed state.
#
# Two deliberate details, both from players repeatedly reporting the destiny tree
# missing for game-start tags (Workshop: Austria 2026-06-13, Bohemia 2026-07-16,
# Bohemia + Poland 2026-07-27) even though this handler was supposed to cover them:
#
#  1. The `_formed` variables are set HERE, not left to the event's options. Destiny
#     advance visibility keys off nd_TAG_formed, so tying it to the player answering
#     a popup makes an entire content tree depend on a popup being delivered. Setting
#     it directly makes the tree appear whatever happens to the event.
#  2. The event fires on a 3-day delay rather than during game setup, so it arrives in
#     a running game with a live event queue. The option still grants the timed
#     modifier and sets nd_TAG_path_*, which the destiny branches need.
#
# Setting the variable twice (here and again in the event option) is harmless: the
# guard below has already been evaluated, and set_variable is idempotent.
#
# The formation event's own fire-guard is a SEPARATE variable, nd_TAG_e1_done,
# not nd_TAG_formed. Keeping them separate is what lets point 1 above stay true.
# Formation events moved off fire_only_once on 2026-08-06 because it is per
# CAMPAIGN, so a game-start tag burned the event for every later former
# (Workshop report ewobmrk, Tibet). Had that guard reused nd_TAG_formed, this
# pre-set would make the queued event fail its own trigger, and restoring the
# event would have meant deleting the pre-set and putting destiny visibility
# back at the mercy of a delivered popup: the exact bug points 1 and 2 exist to
# prevent.
#
# DAH and YUA are the exception: their nd_<tag>.1 is an advance-gated DHE, not
# a formation event, so nothing would ever set their variables. They keep the
# pre-set and lost the day-3 call, which always failed the advance trigger.
#
# HOOK: monthly_country_pulse.effect (its `on_actions` is vanilla-owned).
# Was on_game_start.effect, which vanilla discarded. Runs per country per

# `NOT = { has_variable = nd_TAG_formed }` guards remain, so a tag that
# formed normally is never re-bootstrapped.
#
# Cost of moving off game start: the event now arrives within the first
# month rather than on day 3. Upside: because the flag lives in the save,
# an EXISTING save that never got bootstrapped is repaired on load.

			}
			else_if = {
				limit = { can_form = formable_country:DNM_f }

			}
			else_if = {
