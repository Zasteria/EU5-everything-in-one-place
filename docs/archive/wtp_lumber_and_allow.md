# Лесопилка и «Мериносовая шерсть» — две дыры, измеренные и закрытые 2026-09-12

Обе пришли из его списка после партии ([`../investigations/wtp_backlog.md`](../investigations/wtp_backlog.md)),
обе закрыты в тот же день, и обе стоит держать записанными: каждая была **тихой**
— мод отвечал уверенно и неправильно.

## 1. Лесопилки нет в моде вовсе — **причина найдена и измерена**

«Мод вообще не берёт в расчёт лесопилки… выбрав древесину в окне редактора…
мод напишет, что "товар стоит везде где может". Однако… его стоит в целом 0.»

**Причина — одна строка генератора.** `generate.py:methods()` оставляет только
методы, у которых есть сырьевой вход:

    rows = [m for m in game.methods if m.raw_inputs(game.raw_goods)]

`lumber_mill` (рус. «Лесопилка») производит `lumber` из `tools = 0.417` и
больше ни из чего — его `location_potential` это `vegetation = woods/forest/
farmland/jungle` и `NOT = { raw_material = goods:lumber }`. Сырьевого входа нет
→ метод выброшен → в файлах мода `lumber_mill` **не встречается ни разу**
(проверено `grep` по `in_game/common`). Остаются только `shoen` (японское
уникальное) и `nd_liv_dampfsagewerk` (ND) — оба почти никому не доступны,
поэтому список «где производить лесоматериалы» и выходит пустым.

**Он прав, что это класс, а не случай.** Фильтр выбрасывает **15 методов из
705** (посчитано на сборке с чужими модами):

| товар | здание | метод |
| --- | --- | --- |
| lumber | `lumber_mill` | `lumber_mill_maintenance` |
| wild_game | `forest_village` | `hunting_lodges` |
| liquor | `distillers_guild`, `distillers_workshop` | `beer_liquor_*_maintenance` |
| slaves_goods | `slave_market` | `slave_market_maintenance` |
| stone | `shoen` | `shoen_quarries_maintenance` |
| tools | `iron_mill` | `steel_tools` |
| books, fruit, goods_gold, maize, pearls, pepper | шесть зданий ND | — |

**Ни одного товара это не лишает целиком** (проверено: множество товаров,
которые производят только выброшенные методы, пусто) — но лишает лучшего
способа, а `forest_village` это ещё и одна из четырёх деревень.

**Что с ними делать, кроме как перестать выбрасывать.** У такого метода
`shares()` пуст, значит `_g<n>` = 0 везде — генератор эту ветку уже умеет («A
recipe no RGO can feed»), а `fed_floor` для него равен базе, то есть земля его
кормит всегда. Порядок внутри товара он не ломает: `_m` это выпуск, и
`lumber_mill` (1.0) честно бьёт `shoen` (0.6).

## 8. Фильтр доступных стране способов пропускает чужое — **причина найдена**

«Тонкое сукно показывает, что расчитывает на метод "Мериносовая шерсть", которая
очевидно доступна хер пойми кому, но точно не мне.»

«Мериносовая шерсть» = `spanish_cloth_workshop_maintenance`. **Ворота стоят на
самом методе, а не на здании:**

    spanish_cloth_workshop_maintenance = {
        allow = { custom_tooltip = { text = has_unlocked_spanish_cloth_industry
                                     has_variable = spanish_cloth_industry } }

`method_gates()` читает **только** продвижения метода и `country_potential`
**здания** — `allow` внутри самого метода не читает никто. Поэтому метод стоит
в `bag_wtp_generated_values.txt` без единых ворот.

**Класс измерен и он крошечный.** Собственный `allow` несут семь блоков на всю
сборку, и пять из них — крепостные житницы, которые **не производят ничего** и
методами не являются вовсе (`produced` у них нет; в список они попали только
потому, что внутри их условия стоит `is_produced_in_market`). Остаются два:

| метод | условие | чьё |
| --- | --- | --- |
| `spanish_cloth_maintenance`, `spanish_cloth_workshop_maintenance` | `has_variable = spanish_cloth_industry` | страны (событие Кастилии) |

**Скоуп переменной выбран, а не измерен**: сам `allow` пишет `scope:target`,
когда хочет локацию, значит по умолчанию он не в локации, а переменную,
выдаваемую национальным событием, естественно искать на державе. Если окажется
иначе — метод исчезнет у всех, Кастилию включая; это единственное, что в правке
может ошибиться, и увидеть это можно только партией за Кастилию.
